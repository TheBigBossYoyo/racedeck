# Optional Feed → Feature Availability Map

Companion reference for `IMPROVEMENT_OPPORTUNITIES.md` item #25 ("Missing Feeds / Optional Feed Fallback Documentation"). Everything below was verified against the current source — field names, provider behavior, and widget behavior are all cited to a file/line, not assumed.

Note on naming: item #25's gap description says "WeatherDataSeries" — the real raw feed topic is **`WeatherData`** (`src/renderer/core/providers/F1LiveProvider.ts:823`). The other four names in the gap description (`TyreStintSeries`, `TeamRadio`, `PitLaneTimeCollection`, `TlaRcm`) match the code exactly.

---

## 1. Overview

RaceDeck's `DataProvider` abstraction (`src/renderer/core/providers/types.ts`) defines one `RaceSnapshot` shape that all three providers — `F1LiveProvider`, `DemoProvider`, `OpenF1Provider` — must return. Most `RaceSnapshot` fields (`timing`, `laps`, `stints`, `raceControl`, `weather`, `positions`, …) are non-optional and every provider fills them in, even if with degraded/derived data.

A second group of fields is declared **optional** on `RaceSnapshot` (`types.ts:59-92`): `lapPositions`, `sessionBests`, `pitLaneTimes`, `teamRadio`, `currentTyres`, `tyreStintHistory`, `feedFreshness`, `trackMessage`, `sessionClock`. These map 1:1 to raw F1 live-timing topics that only exist on F1's own SignalR feed — `LapSeries`, `TimingStats`, `PitLaneTimeCollection`, `TeamRadio`, `CurrentTyres`, `TyreStintSeries`, (computed from freshness), `TlaRcm`, `ExtrapolatedClock` respectively (`F1LiveProvider.ts:820-837`).

**Two different mechanisms track "is this data available," and they don't cover the same fields:**

1. **`DataAvailabilityMap`** (`src/shared/models/index.ts:371-385`, built with `emptyAvailability()` in `types.ts:149-162`) is a fixed struct of 10 booleans: `timing, laps, stints, intervals, raceControl, weather, positions, positionProgress, telemetry, live`. All three providers populate every one of these flags on every snapshot (e.g. `DemoProvider.ts:434-445`, `OpenF1Provider.ts:372-383`, `F1LiveProvider.ts:990-1009`), and widgets like `WeatherPanel.tsx:93` and `RaceControlFeed.tsx:46` gate a real `EmptyState` off `snapshot.availability.X`.
2. **The nine optional `RaceSnapshot` fields above have no corresponding availability flag at all.** There is no `availability.teamRadio`, no `availability.tyreStintHistory`, etc. Their presence/absence is signaled only by the field itself being `undefined` (provider never touched it) vs. an array/object (provider populated it, possibly empty). This is a real, confirmed gap: a widget has no single boolean to check "is this feed supported by the current provider" — it has to infer that from whether the array happens to be empty right now, which conflates "provider doesn't support this feed" with "provider supports it but nothing has happened yet" (e.g. no radio traffic yet this session).

`SystemStatus.ts` (`src/renderer/core/engines/SystemStatus.ts`) is a third, unrelated status surface — it aggregates connection/auth/sync/DRM degradation (`sessionError`, `liveStatus`, `followStatus`, `drmCapable`, `enrichmentIssue`) into a generic list of `SystemStatusEntry` for a diagnostics banner. It says nothing about which of the nine optional feeds above are present; it is not a `DataAvailabilityMap`-like per-feed construct for this purpose.

**Net effect:** absence of one of the nine optional fields is handled **per-widget, ad hoc**, not through one shared mechanism. Some widgets fall back gracefully (derive an equivalent from data they do have), some hide a sub-section silently, and a couple already show a tooltip explaining *why* — but there's no single pattern applied consistently, and no reusable "this feed isn't available" flag to hang a badge off of.

All nine rows above share one fact: **`DemoProvider.ts` and `OpenF1Provider.ts` never assign any of these nine fields** — confirmed by grepping both files for each field name (only `weather`/`weatherHistory` construction appears in either). Every one of these fields is `undefined` for every Demo and OpenF1 session, always.

For contrast, `weather?: WeatherSample | null` / `weatherHistory: WeatherSample[]` are populated by **all three** providers (`DemoProvider.ts:419-420,432`, `OpenF1Provider.ts:358-359,370`, `F1LiveProvider.ts:940-946,964`) and are gated by the real `availability.weather` flag — this is the one optional-in-spirit feed that got full `DataAvailabilityMap` treatment, and it shows in how cleanly `WeatherPanel.tsx:93-99` handles its absence (see §3).

## 3. Degradation behavior per feature (verified in widget code)

| Widget / feature | Feed it depends on | What actually happens when the feed is missing |
|---|---|---|
| `driverDossier/TyreHistoryDrawer.tsx` (opened from `TyrePanel.tsx:266-268`), set-label ("M2") in `TyrePanel.tsx:199,243` | `tyreStintHistory` | Silent hide with graceful degradation on the label: `read.stintHistory` is `null` so the drawer's condition (`TyrePanel.tsx:266`) is false and it never renders; `buildSetLabel` (`TyreRead.ts:236-247`) returns `null` without history, so no "M2"-style tag shows. **However**, the "used set" note right above it (`TyrePanel.tsx:250-264`) already carries a `ProvenanceBadge` with `detail="TyreStintSeries has not reported this driver yet - age inferred from TimingAppData"` (`TyrePanel.tsx:255-261`) — this is the one place in the codebase that already explains a missing optional feed to the user inline. |
| `driverDossier/PitHistoryPanel.tsx` | `pitLaneTimes` | **Fully silent.** `buildPitStopHistory` (`PitHistory.ts:80`) falls back to `[]`; the component itself returns `null` when `stops.length === 0` (`PitHistoryPanel.tsx:24`) — no empty-state text, no tooltip, the whole panel simply doesn't exist in the DOM. Indistinguishable from "this driver just hasn't pitted yet." |
| `PitEventLogPanel.tsx` (`pit-log`, field-wide pit-stop log) | `pitLaneTimes` (duration only); stops themselves also come from `laps` (`isPitInLap`/`isPitOutLap`) and `stints` boundaries, compounds from `stints` (which the live provider already reconciles with `currentTyres`) — the same feeds as per-driver pit history, plus `laps`/`stints` that every provider fills | **Degrades per column, not as a whole.** On Demo/OpenF1 (no `pitLaneTimes`) the stops, in/out laps and tyre change still appear, derived from lap flags and stint boundaries, but the pit-lane time reads "—" — it is never estimated. With no stops at all it renders `EmptyState` "No pit stops yet" (again indistinguishable from "this feed can't supply them"; see recommendation 6). Rows are clipped to the playback clock, so scrubbing back removes them. A lap, compound or duration the feed did not report is "—", never a default. |
| `StrategyInsightsPanel.tsx` "slow stop" insight | `pitLaneTimes` | Silent omission of one insight, not the whole panel: `analysePitLane` returns `null` on insufficient data (`StrategyEngine.ts:257`), so `generateInsights` (`StrategyEngine.ts:941-959`) simply never pushes that insight. Other insight kinds (safety-car window, degradation, etc.) still show normally. |
| `TeamRadioPanel.tsx` | `teamRadio` | Real `EmptyState`, but the copy is misleading for a provider that structurally can't ever supply radio: `ordered.length === 0` → `<EmptyState title="No team radio yet" hint="Clips appear as F1 broadcasts them during the session." />` (`TeamRadioPanel.tsx:101-105`). On Demo/OpenF1 this message implies clips *might* arrive later, when in fact they never will for that provider. |
| `DossierRadioList` inside `DriverDossier.tsx` | `teamRadio` | **Fully silent.** `model.radioClips.length > 0 && <DossierRadioList .../>` (`DriverDossier.tsx:373`) — zero clips renders nothing at all, no empty-state, no note. |
| `RaceControlFeed.tsx` sticky ticker | `trackMessage` | **Fully silent.** `{snapshot.trackMessage && (...)}` (`RaceControlFeed.tsx:62-66`) — when `null`/`undefined` the ticker line simply doesn't render; the message list below it is unaffected and still gated by the real `availability.raceControl` flag (`RaceControlFeed.tsx:46-52`), which is a separate, always-populated feed. |
| `QualifyingMonitor.tsx` countdown timer | `sessionClock` | **Graceful, tiered fallback with an explicit label** — the best-handled case in the codebase. Order of preference: `snapshot.sessionClock` (feed-authoritative) → `phaseClock` (derived from the session timeline) → raw `duration - clock`. When neither of the first two is available, the timer's `title` attribute is explicitly set to `'Session time remaining (phase clock unavailable)'` (`QualifyingMonitor.tsx:84`) instead of pretending the number is the authoritative segment clock. |
| `PositionTrendChart.tsx` | `lapPositions` | **Graceful derivation, not a hide.** `useOfficial = officialMaxLap >= 2` (`PositionTrendChart.tsx:72`); when false, the chart falls back to deriving cumulative race time per lap from `snapshot.laps` directly (`PositionTrendChart.tsx:76-100`), only returning `null` (chart entirely absent) if there aren't even 2 laps of raw lap data either (`PositionTrendChart.tsx:74,85`). The file's own header comment (`PositionTrendChart.tsx:12-24`) documents this fallback as intentional. |
| `DriverDossier.tsx` `SpeedMarks` row | `sessionBests` | **Fully silent.** `speeds` is `null` when no matching entry exists (`DriverDossier.tsx:114-120`); `{speeds && <SpeedMarks .../>}` (`DriverDossier.tsx:310`) then renders nothing — no placeholder, no "not available on this session" note. |
| `DriverComparisonCard.tsx` I1/I2/FL/Trap delta rows | `sessionBests` | **Fully silent, whole-group hide.** `(bestsA || bestsB) && SPEED_MARKS.map(...)` (`DriverComparisonCard.tsx:269-282`) — if neither compared driver has `sessionBests`, all four rows vanish together with no indication they exist as a feature at all. |
| `TimingTower.tsx` stale badge, `TrackMap.tsx` stale badge, `DriverDossier.tsx`'s `ErsGauge` `staleMs` | `feedFreshness` | **Correctly inert outside live**, by design: `formatStaleness(ms, threshold)` (`src/renderer/lib/utils.ts:46-49`) returns `null` when `ms == null`, so passing `snapshot.feedFreshness?.TimingData` (undefined on Demo/OpenF1, and on any non-live F1LiveProvider session) simply never shows a "STALE" badge — which matches the field's own contract ("meaningless for anything but a LIVE session," `types.ts:73-74`). Not a gap; the fallback is exactly right. |
| `TimingTower.tsx` per-driver stale marker (`DriverStaleMarker`, clock icon + "18s") | `driverFreshness` (per driver, per feed: TimingData / Position / CarData; built by `DriverFeedTracker`) | **Correctly inert outside live**, like `feedFreshness`: `snapshot.driverFreshness` is `undefined` on Demo, OpenF1 and any non-live F1LiveProvider session, so no marker is ever shown. In live sessions a driver never seen on a feed is left **absent** (never treated as fresh), and the marker is skipped for retired or in-pit cars and when the whole feed is already stale, since the existing badges cover those. Thresholds match the feed-level ones (timing 15 s, position/telemetry 5 s). The marker is an icon plus text, not colour only. |
| `StatusBar.tsx` "Enriching telemetry: …" chip (`describeEnrichmentProgress` in `SystemStatus.ts`) | `ProviderDiagnostics.enrichmentProgress` (per feed: position, carData) | Shown only while F1LiveProvider is loading Position/CarData in chunks for an archive session; null for live sessions and after `cancelPendingLoads()`. It reports only what was measured: session time covered against `getDuration()`, or just what has arrived when the length is unknown. **No percentage and no ETA**, because the main process does not send a total point count. A failed feed is marked `failed` and surfaces through `enrichmentIssue` instead. It is listed as ongoing progress and does not count as an "issue". |
| `TrackMap.tsx` position dead-reckoning (`trackMap/positionTracking.ts`) | `feedFreshness.Position` | Also inert by design: gated behind `isLiveSnapshot && hasCoordinatePositions` (`TrackMap.tsx:192`) before `reconcileLivePositions` is ever called, and defaults the freshness value to `0` (never stale) when absent (`TrackMap.tsx:198`) — consistent with the field being genuinely absent only outside live, where this code path doesn't run anyway. |
| `WeatherPanel.tsx` | `weather` / `weatherHistory` (not one of the nine gapped fields, shown for contrast) | **The one fully correct pattern.** Gated by the real `availability.weather` flag: `if (!snapshot || !snapshot.availability.weather || !w) return <EmptyState title="No weather data" hint="Weather telemetry will appear here." />` (`WeatherPanel.tsx:93-99`) — clear, provider-agnostic, and grounded in an actual capability flag rather than an incidental empty array. |

**Pattern summary:** of the nine gapped optional fields, one (`sessionClock`) degrades with an explicit "why" label, one (`lapPositions`) degrades with a genuine data-equivalent fallback, one (`tyreStintHistory`, via `TyrePanel`'s used-set note) already carries a `ProvenanceBadge` tooltip — and the rest (`pitLaneTimes`, `teamRadio`, `trackMessage`, `sessionBests`, `currentTyres`) degrade by simply rendering nothing, with `TeamRadioPanel` being the sole case with an empty state, and that empty state's copy doesn't distinguish "provider doesn't support this" from "nothing has happened yet."

## 4. Recommendations

1. **Reuse `ProvenanceBadge` (`src/renderer/components/ui/primitives.tsx:135-153`) as the standard affordance**, rather than inventing a new component. It already renders a `title`-tooltip badge and is already used for exactly this purpose in `driverDossier/TyrePanel.tsx:255-261` and `WeatherPanel.tsx` (via `ProvenanceBadge` import at `WeatherPanel.tsx:4`). The pattern to copy: pass `provenance="insufficient"` with a `detail` string naming the feed by its real topic name, the same way the tyre panel says `'TyreStintSeries has not reported this driver yet...'`.

2. **`driverDossier/PitHistoryPanel.tsx:24`** — instead of `if (stops.length === 0) return null`, render a small inline note (or a `ProvenanceBadge`) explaining that pit-history requires F1's `PitLaneTimeCollection` feed, only available via `F1LiveProvider`. This directly matches item #25's own suggested example ("pit history requires PitLaneTimeCollection + CurrentTyres").

3. **`TeamRadioPanel.tsx:101-105`** — split the empty-state copy in two: keep "No team radio yet" for an F1LiveProvider session with genuinely no clips so far, but show a distinct message (e.g. "Team radio isn't available on this session source") when the active provider is Demo/OpenF1. Since there's no `availability.teamRadio` flag to check today (see §1), this requires either adding one to `DataAvailabilityMap` or checking `providerCapabilities.id` from `ProviderCapabilities` (`types.ts:28-40`) at the call site.

4. **`DriverDossier.tsx:310`** (`{speeds && <SpeedMarks .../>}`) and **`DriverComparisonCard.tsx:269-282`** (`(bestsA || bestsB) && SPEED_MARKS.map(...)`) — both currently omit their row(s) with zero explanation. A one-line `title`-only hint ("Speed-trap/intermediate marks require F1's TimingStats feed") next to wherever the section header would have gone would close the "silently renders nothing" gap item #25 calls out, without needing a full redesign.

5. **`RaceControlFeed.tsx:62-66`** — the sticky `trackMessage` ticker has no fallback text at all when absent; since it's a "nice to have ahead of the full message" rather than core content, a low-effort fix is simply leaving it blank as today but is worth a one-line code comment (there currently is a good one at lines 59-61) confirming this is deliberate, so a future contributor doesn't "fix" it into a distracting always-visible placeholder.

6. **Longer-term structural fix**: extend `DataAvailabilityMap` (`src/shared/models/index.ts:371-385`) with flags for the nine gapped fields (e.g. `teamRadio`, `pitLaneTimes`, `tyreStintHistory`, `sessionBests`, `lapPositions`, `trackMessage`, `sessionClock`), each provider setting them explicitly (`true` only for `F1LiveProvider` when the corresponding raw array is non-empty at ingest, `false` unconditionally for `DemoProvider`/`OpenF1Provider`). This turns "is the array empty" (ambiguous between "not supported" and "nothing happened yet") into an unambiguous boolean every widget in §3 can check the same way `WeatherPanel.tsx:93` already checks `availability.weather` — the one place in the codebase where this problem doesn't exist today.
