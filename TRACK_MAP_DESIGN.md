# Track Map Widget Architecture

Scope: `src/renderer/widgets/TrackMap.tsx`, `src/renderer/widgets/trackMap/*`, the outline math in `src/renderer/core/providers/f1normalize.ts` + `src/renderer/core/providers/F1LiveProvider.ts`, and the coordinate math in `src/renderer/core/engines/geometry.ts`.

## 1. Overview

**Component:** `TrackMap()` in `src/renderer/widgets/TrackMap.tsx`.

**Data it consumes**, all read from `useSessionStore((s) => s.snapshot)` (a `RaceSnapshot`, `src/renderer/core/providers/types.ts:43`):

- `snapshot.positions: PositionSample[]` — the raw per-driver feed. Each sample (`src/shared/models/index.ts:324`) carries `driverNumber`, `date`, `x`/`y`/`z` (track-space provider units, nullable), `position` (classification), and `lapProgress` (0..1, only populated when x/y are unavailable — a schematic fallback derived from real lap/sector timing, "never faked").
- `snapshot.drivers: Driver[]` — static roster metadata (`number`, `code`, `teamColour`, etc., `src/shared/models/index.ts:91`), joined into a `Map` keyed by `number` (`meta` in `TrackMap.tsx:101`).
- `snapshot.timing: TimingEntry[]` — used to derive `retiredDrivers` (`retired || status === 'RETIRED' || status === 'DNF'`), `inPitDrivers` (`inPit || status === 'IN_PIT'`), and `fastestDriver` (`entry.isFastestLap`).
- `snapshot.trackPath?: {x,y}[]` — the precomputed circuit outline trace (built upstream in `F1LiveProvider`/`f1normalize.ts`, see §2).
- `snapshot.availability: DataAvailabilityMap` — specifically `positions` (real x/y available), `positionProgress` (schematic fallback available), and `live` (streaming vs replay/historical).
- `snapshot.feedFreshness?.Position` — wall-clock ms since the `Position` topic last delivered data (live only).
- `snapshot.trackStatus`, `snapshot.session.id` — for tinting the outline and keying the sticky viewing frame.
- Settings/session state outside the snapshot: `useSettingsStore` (`favorites`, `performanceMode`, `theme.reducedMotion`) and `useSessionStore` (`focusDriver`, `playing`, `getDiagnostics()`).

**What it renders:** an SVG (`viewBox="0 0 300 200"`) containing either (a) the traced circuit outline as a `<polyline>` plus one `TrackMapDriverMarker` per driver dot, in coordinate mode, or (b) a stylized fixed oval (`pointAt()`) with dots placed by lap progress, in schematic mode. It also renders a `WidgetFrame` with badges ("Schematic" / "Live positions", a staleness badge, and a "Tracing outline…" badge with a diagnostics tooltip while no outline exists yet), and an `EmptyState` when neither positions nor positionProgress are available (with a distinct message when live position data is gated behind an F1 TV login).

## 2. Pipeline stages

### Stage 0 — Outline generation (upstream, in the provider layer)

This does **not** happen in `TrackMap.tsx` or `geometry.ts` — it happens once per session in `F1LiveProvider` (`src/renderer/core/providers/F1LiveProvider.ts`) calling into pure functions in `src/renderer/core/providers/f1normalize.ts`. `TrackMap.tsx` only ever reads the finished `snapshot.trackPath`.

1. **`pickReferenceDriver(points)`** (`f1normalize.ts:692`) — scans every accumulated `Position` stream point, counts on-track samples per driver number (`isOnTrackEntry`, which rejects `Status: "OffTrack"` and the feed's `(0,0)` "no fix" sentinel — `f1normalize.ts:849`), and picks whichever driver has the *most* samples so far. This runs on every ingest until an outline closes; the comment at `f1normalize.ts:680-690` documents that an earlier hard cap of 600 raw points was proven wrong by live diagnostics (600 points can be a few seconds of the real per-car incremental cadence), so there is now no cap — a single cheap pass, called a few times a second, that short-circuits once closure succeeds.
2. **`buildTrackPath(points, maxPoints=700, minDistance=150)`** (`f1normalize.ts:707`) — follows only the reference driver's samples, downsampling: a point is kept only if it's more than `minDistance` (150 provider units) from the last kept point, capped at `maxPoints` (700, chosen to cover ~7 laps' worth of search window at Zandvoort-scale spacing per `f1normalize.ts:657-667`).
3. **`buildClosedTrackPath(points, ...)`** (`f1normalize.ts:793`) — takes that downsampled path and looks for a **lap closure**: a pair of indices `(j, i)` with `i > j` where (a) cumulative distance from `j` to `i` exceeds `MIN_CLOSED_LAP_UNITS` (30,000 units — a plausible minimum full-lap distance) and (b) the endpoints are within `closeDistance` of each other (`max(minDistance*2, median-step*1.5)`, since real inter-sample spacing at racing speed is ~45m, well over the 150-unit thinning distance). **Among all valid `(j, i)` pairs, the tightest (smallest) geometric distance wins — not the first one found in scan order.** This was a real bug (see §5): scanning in index order could lock onto a short pit-lane loop (which commonly runs close to the main straight and can close its own distance/proximity checks) before the true full-lap closure was reached. The function returns only the closed **prefix** `path.slice(j, i+1)` plus a repeat of `path[j]` to close the polygon — not the whole traced route, which would otherwise stack multiple laps into a scribble.
4. **`F1LiveProvider.adoptTrackPath(allowOpenFallback)`** (`F1LiveProvider.ts:506`) — the caller. Once `trackPathClosed` is true it never recomputes (both for cost and immutability of a proven outline). It tries `buildClosedTrackPath` first; only when that fails and `allowOpenFallback` is set (true for both live and replay) does it fall back to the raw open `buildTrackPath` result, gated by `MIN_OPEN_TRACE_POINTS = 30` so a first-poll squiggle is never shown. **Only the closed branch calls `saveTrackPathCache`** — an open/best-effort trace is displayed but never persisted, so it can't corrupt the cache for a later session at the same circuit.
5. **Cross-session caching** — `trackPathCacheKey(sessionId, feedPath)` (`F1LiveProvider.ts:426`) keys the cache by *meeting* (first two path segments), not by individual session, under a namespace `v${TRACK_PATH_CACHE_SCHEMA_VERSION}/...`. `TRACK_PATH_CACHE_SCHEMA_VERSION` is currently `3` (`F1LiveProvider.ts:131`) and is deliberately bumped whenever the closure *algorithm* changes shape, not just the cache format — so an outline cached under an older, buggier closer is treated as a miss and rebuilt rather than silently reused (this is exactly what caught the pit-lane-loop bug, see §5). `loadCachedTrackPath` validates the cached array's length (`20..TRACK_PATH_CACHE_MAX=700`), every point's finiteness, and that the first/last points match (i.e., it really is a closed polygon) before trusting it.
6. **Diagnostics** — `debugTrackTraceInfo(points)` (`f1normalize.ts:741`) and the provider's `getDiagnostics()` expose `trackRawPointCount`, `trackReferenceDriver`, `trackOpenTraceLength`, `trackAdoptedLength`, `trackPathClosed`, surfaced in `TrackMap.tsx`'s "Tracing outline…" badge tooltip (`TrackMap.tsx:302-319`) specifically so a stuck outline can be diagnosed (no reference driver found vs. found-but-not-accumulating vs. accumulating-but-not-closing) without guessing.

### Stage 1 — Framing / bounds (`TrackMap.tsx`, `geometry.ts`)

- `calculateBounds(points)` (`geometry.ts:17`) computes a min/max box, with a degenerate-case guard (`minX===maxX` etc.) that pads by ±1 so a single point or a fully-flat set never produces a zero-size box (which would divide by zero during normalization).
- `traceBounds = calculateBounds(trace)` where `trace = snapshot.trackPath ?? []`.
- **Sticky frame, keyed on session id only** (`frameRef`, `TrackMap.tsx:88,131-141`): the frame is *not* reset when the trace changes length or goes from open to closed. Instead, every render **unions** `frameRef.current.bounds`, `traceBounds`, and `calculateBounds(currentPoints)` (live car positions) via `unionBounds` (`geometry.ts:53`) — a box can only ever grow, never shrink or reset, across the life of one session id. This specifically guards two related bugs (see §5): a newly-available or newly-upgraded outline used to replace rather than extend the frame, snapping drivers standing in not-yet-traced track sections outside the drawn loop and producing a multi-second reflow/flicker.
- `unionBounds` also independently guards against off-panel cars: a pit lane or run-off excursion outside the racing-line trace is included in the box rather than clipped.

### Stage 2 — Coordinate projection (`geometry.ts`)

- `normalizePoint(p, bounds, config)` (`geometry.ts:75`) maps a raw `{x,y}` into the `300×200` viewBox with 15px padding, preserving aspect ratio (`scale = min(scaleX, scaleY)`), centering the shorter axis, and **flipping the Y axis** (`viewBoxHeight - (...)`) because provider telemetry coordinates are right-handed/Y-up while SVG is Y-down.
- `normalizePoints` is a thin per-point map used to build the outline `<polyline>` string; each driver dot is normalized individually via `normalizePoint`.
- Critically, the outline and every car are normalized **against the exact same `currentBounds`** computed in Stage 1 (`TrackMap.tsx:143-166`) — the code comment there is explicit that using two different frames for the track vs. the cars would desynchronize them.
- Schematic mode bypasses all of this: `pointAt(progress)` (`TrackMap.tsx:45`) places a dot directly on a fixed decorative ellipse (`CX=150, CY=100, RX=120, RY=74`), independent of `geometry.ts`.

### Stage 3 — Dot construction & dead reckoning (`TrackMap.tsx`, `trackMap/positionTracking.ts`)

- In coordinate mode, one `DriverDot` (`trackMap/types.ts`) is built per position sample with non-null x/y, joined against `meta`, `retiredDrivers`, `inPitDrivers`, `fastestDriver`.
- **Only when `isLiveSnapshot && hasCoordinatePositions`**, two extra passes run (this logic has no meaning for replay, which has no "now" to extrapolate toward, or schematic mode, which has no x/y velocity):
  - `reconcileLivePositions(dots, positionTrackRef.current, nowMs, feedFreshnessMs, POSITION_STALE_MS=5000, MAX_EXTRAPOLATION_DISTANCE)` (`positionTracking.ts:70`): for each dot, `updatePositionTrack` folds the new reading into a rolling `PositionTrack {x,y,vx,vy,updatedAtMs}` — a reading within `MIN_MOVE_EPSILON=0.01` viewBox units of the last one is treated as "frozen" and does *not* update velocity/time, so both stay anchored to the last genuine movement. If the feed is stale (`feedFreshnessMs >= 5000`) **and** the current reading was frozen (didn't move the track), the dot's position is replaced by `extrapolatePosition` — projecting forward by last-known velocity, capped to `MAX_EXTRAPOLATION_DISTANCE = 0.05 * hypot(300,200)` (≈5% of the viewBox diagonal) — and flagged `extrapolated: true`.
  - `fillMissingFromTracks(reconciled, positionTrackRef.current, buildDot, nowMs, MAX_EXTRAPOLATION_DISTANCE, POSITION_STALE_MS)` (`positionTracking.ts:105`): guards the *complementary* failure mode — a driver entirely **absent** from this frame's real positions (not just frozen), which would otherwise vanish for exactly one tick and reappear the next. For every tracked driver not present in `reconciled`, if their track is younger than `maxOutageMs` it synthesizes a dead-reckoned dot (again capped and flagged `extrapolated: true`) via the caller-supplied `buildDot`, which itself returns `null` (dropping the driver) if they're retired or missing timing/roster metadata.
- Final dots are sorted by classification position (`(b.position ?? 99) - (a.position ?? 99)`, i.e. descending, so later/undefined positions are painted first and leaders end up drawn last/on top).

## 3. Marker animation lifecycle (`TrackMapDriverMarker.tsx`)

- A single shared `AnimationFrameBatch<number, ActiveDotAnimation>` (`src/renderer/lib/AnimationFrameBatch.ts`) drives **all** marker animations off one `requestAnimationFrame` loop, keyed by driver number, rather than one rAF loop per marker.
- On each prop update (`useLayoutEffect`, keyed on `[animate, dot.number, dot.x, dot.y, durationMs]`):
  - The previous rendered position is read from `positionRef.current` (a per-marker ref, not state — avoids a re-render per animation frame).
  - `dotAnimations.cancel(dot.number)` stops any in-flight animation for this driver first.
  - **Large-jump guard:** if `!animate` or the jump distance exceeds `70` viewBox units, the marker **snaps** instantly to the new position (`element.setAttribute('transform', ...)`) instead of animating — this avoids a visually nonsensical "glide" across the whole map when a driver teleports (e.g. after a genuinely stale feed resumes, a session/lap reset, or first appearance).
  - Otherwise it schedules a linear interpolation from `from` to `to` over `durationMs`, computed per animation-frame tick as `from + (to - from) * min(1, (now - started) / durationMs)`, writing directly to the DOM (`element.setAttribute('transform', 'translate(x, y)')`) and updating `positionRef.current` — again bypassing React re-renders for the moving part.
  - `durationMs` and whether to animate at all come from `trackMapAnimationConfig()` in `TrackMap.tsx:50`: live snapshots animate over `900ms` (`1000ms` under performance mode) matching the roughly-2Hz Position feed cadence; replay animates over a much shorter `280ms` (`620ms` in performance mode) tied to playback tick rate; animation is disabled entirely when `reducedMotion` is set, or when replay is paused (`!playing`) and not live.
- **Graceful degradation on stale/missing data** happens one layer up (Stage 3, `positionTracking.ts`), not inside the marker itself — the marker only reacts to `dot.extrapolated`:
  - `markerOpacity` drops to `0.55` when `dot.extrapolated` is true (vs. `0.42` for merely retired/in-pit and unfocused, `1` otherwise).
  - The marker's outer circle gets a dashed stroke (`strokeDasharray: '2 1.5'`) when extrapolated, as a persistent visual "this is estimated" cue distinct from opacity alone.
  - The `aria-label` appends `", estimated position — feed stalled"` when extrapolated, so the degradation is also conveyed non-visually.
- Marker radius is `getTrackMapMarkerRadius(focused)` — `7` when focused, `5.5` otherwise (also reused by `labelLayoutPlacement.ts`'s marker-avoidance boxes, though those use slightly larger `10`/`8.5` radii to keep labels clear of the marker's hit area, not just its drawn circle).
- Outline color priority: fastest lap (purple) > focused (accent) > team color. Label fill: fastest lap (purple) > faded-and-unfocused (muted) > normal foreground.
- The marker `<g>` is a focusable, clickable element (`role="button"`, `tabIndex=0`, Enter/Space handling) calling `onFocus(dot.number)` — this is how clicking a car on the map sets `focusDriver` app-wide.

## 4. Label layout rules (`trackMap/labelLayout.ts` + `trackMap/labelLayoutPlacement.ts`)

`placeTrackMapLabels(labels, previousPlacements?)` runs once per render over **all** dots together (not per-marker), because avoiding overlap requires knowing every other label's placement.

1. **Priority ordering** (`compareTrackMapLabels`): labels are processed focused-first, then favorited, then fastest-lap-holder, then by classification position, then by driver number (`getTrackMapLabelPriority`: focused=+8, favorite=+4, fastestLap=+2). Higher-priority drivers get first pick of the best candidate slot, so a crowded field trades off *away* from low-priority labels first.
2. **Candidate search** (`chooseTrackMapPlacement` + `buildPlacementCandidate` in `labelLayoutPlacement.ts`): for each of 2 ring offsets (`CANDIDATE_RINGS = [0, 10]`) × 8 compass directions (`CANDIDATE_DIRECTIONS`, ranked 0-7, N first then diagonals then E/W then S), a candidate label box is built at `markerGap = markerRadius + 8 + ringOffset` from the dot, clamped to stay inside the `300×200` viewBox (`clampAxis`, `EDGE_PADDING=2`).
3. **Penalty scoring:** `penalty = labelOverlapArea*1000 + markerOverlapArea*100 + rank`. Label-vs-label overlap is penalized 10× more heavily than label-vs-marker overlap (`calculateOverlapArea`, plain axis-aligned box intersection), and `rank` (direction preference, north-biased) only matters as a tiebreaker. The search **short-circuits** the instant a zero-overlap candidate is found (`labelOverlapArea === 0 && markerOverlapArea === 0`); otherwise it keeps the globally lowest-penalty candidate seen across the whole 16-candidate sweep.
4. **Hysteresis (sticky placement)** — added in commit `8d8b7b1`: without it, a marginal recompute each render could snap a label to a different slot every frame as neighboring cars move, reading as jitter. `chooseTrackMapPlacement` re-scores the driver's *previous* placement at the dot's *new* position (`reevaluatePlacementAtNewPosition`, preserving the original dot→label offset) and keeps the old placement unless the freshly-computed best candidate beats it by more than 25% (`hysteresisThreshold = previousPenalty * 0.75`). `TrackMap.tsx` persists `labelPlacementsRef` across renders (keyed by driver number) specifically to feed this previous-placement lookup.
5. **Visibility gating:** even the best candidate is only shown (`visible: true`) for `focused || favorite || isFastestLap` drivers — everyone else gets a computed-but-hidden placement (`visible: false`), so the map doesn't try to label all 20 cars simultaneously.
6. **Rendering the offset:** `TrackMapDriverMarker` reads `labelPlacement.x/y` and computes `labelDx/labelDy` relative to the dot's own `x/y`, then renders the label inside a child `<g transform="translate(labelDx, labelDy)">` with its own independent CSS transition (`200ms cubic-bezier`, only when `animate`) — so the label can glide to a new offset smoothly even while (or independent of) the marker's own rAF-driven position animation.
7. **Text:** `toTrackMapLabelText` appends `" · FL"` to the driver code for the fastest-lap holder. Text width is estimated per-character (`measureCharacterWidth` in `labelLayoutPlacement.ts`) rather than measured from the DOM, with a few hardcoded per-character widths (space, `·`, `I`, default `5.2`) — a coarse approximation, not real font metrics.

## 5. Known fragile points / recent bug history

From `git log --oneline -- src/renderer/widgets/TrackMap.tsx src/renderer/widgets/trackMap/ src/renderer/core/engines/geometry.ts` plus the outline logic's own history in `F1LiveProvider.ts`/`f1normalize.ts` (which live outside those paths, so a plain file-scoped `git log` on the widget alone won't surface them):

- **`28df0ed` — "track outline closure picked the first valid match, not the best one."** `buildClosedTrackPath` scanned `(j,i)` closure candidates in index order and returned the first pair clearing the distance checks. A pit lane commonly runs close to the main straight, so a reference car that pitted early could close on that short pit-lane loop before the true lap closure was ever reached — producing a real-looking-but-wrong outline with the rest of the field rendering outside it. Fixed by scanning the whole bounded search window and keeping the tightest (smallest-distance) match; cache schema bumped `2 → 3` so any outline already cached under the old buggy closer is invalidated.
- **`fd21f4d` — "track map frame bounds reset (not extended) when the outline became available."** The sticky frame used to be keyed on `${sessionId}:${trace.length}`, so the moment the outline appeared or upgraded (open → closed), the key changed and the frame reset to the outline's own (usually smaller) bounds alone, discarding accumulated car-position extent — drivers in not-yet-traced sections rendered outside the loop, then the box slowly re-grew, reading as a multi-second reflow/flicker. Fixed by keying on session id only and unioning the trace's bounds into the existing frame every tick (see Stage 1 above) — this is the current, permanent behavior.
- **`eeb3826` — "progressive track outline, per-driver flicker bridging, and true 5-marker timeline cap."** Three fixes in one: (1) the map previously required a *perfect closed lap* before showing any outline at all, live or replay, with no recovery path if closure ever failed for a given circuit; the open-trace fallback (`MIN_OPEN_TRACE_POINTS=30`) was extended to live sessions, never cached, silently upgraded to closed once real closure succeeds. (2) the existing dead-reckoning only smoothed a driver *present but frozen* in a frame — a driver entirely *absent* for one null sample still flickered off and back on; `fillMissingFromTracks` was added to bridge that case symmetrically. (3) unrelated timeline-scrubber marker cap, not part of the map render pipeline itself.
- **`006b12a` — "add live track-outline diagnostics."** Added `debugTrackTraceInfo`/`getDiagnostics()` (`trackRawPointCount`, `trackReferenceDriver`, `trackOpenTraceLength`, `trackAdoptedLength`, `trackPathClosed`) surfaced in the "Tracing outline…" badge tooltip, purely to make a stuck outline diagnosable in the field rather than guessed at from static code reading.
- **`64ce78b` — "invalidate stale track-path cache..."** (title covers multiple widgets); the track-map-relevant part is the outline cache invalidation path that the schema-version bump mechanism in `F1LiveProvider.ts` builds on.
- **`339ff54` — "revert track map dot regression..."** A prior round's dot-rendering change was reverted; the exact regression isn't detailed in the available commit message beyond the title, so treat any dot-rendering change as worth double-checking against a real live session, not just unit tests.
- **`8d8b7b1` — "...Track Map/Gap Chart polish."** Added label-placement hysteresis (`previousPlacements` param + `reevaluatePlacementAtNewPosition`, §4 item 4) specifically to stop labels snapping to a new slot on every marginal recompute, plus the label's own CSS transition and a larger default widget footprint in the broadcast layout. (This commit also fixed unrelated issues in `TrackStatusBanner`, team-radio CSP, and `GapChart` — not part of the track-map pipeline itself.)
- **`81378ef` — "TrackStatusBanner crashed the whole app on launch (React #185)."** Not a Track Map bug directly, but relevant context: an unrelated component crashing at the app root (a `?? []` selector fallback creating a fresh array reference every render, tripping Zustand's `useSyncExternalStore` into "Maximum update depth exceeded") unmounted the entire React tree, including TrackMap, before any session ever connected. The fix introduced a shared `EMPTY_ARRAY` constant (`src/renderer/lib/utils.ts`) for referentially-stable selector fallbacks — worth knowing about if `TrackMap.tsx` or its store selectors are ever changed to use a `?? []`/`?? {}` fallback, since the same crash class would recur.

## 6. Extension notes

Based only on what's observed above:

- **Never key the sticky frame (`frameRef`) or any similar cache on the *length* or shape of a value that can arrive incrementally** (like `trace.length`). Two real bugs (`fd21f4d` and the caching half of `28df0ed`) trace back to keying state on a value that changes as data streams in rather than on a stable identity like `session.id`. Prefer "union into what's already there" over "replace with the latest computation" for any frame/bounds state that must not visibly reflow.
- **The outline and every car position must be normalized against the exact same `Bounds` object.** `TrackMap.tsx` computes `currentBounds` once per render and threads it into both `normalizePoints(trace, currentBounds, config)` and every `normalizePoint(p, currentBounds, config)` call. If a future change computes the outline's bounds separately from the cars' bounds (e.g. to memoize them independently), the two will desync — this is the exact class of bug `fd21f4d` fixed.
- **Coordinate system:** raw `PositionSample.x/y` are provider (F1 timing feed) track-space units, decimetre-scale, Y-up. `normalizePoint` flips Y for SVG. Any new code touching raw x/y before normalization must account for this — comparing a raw-space distance against a viewBox-space threshold (or vice versa) will silently misbehave. Note `MAX_EXTRAPOLATION_DISTANCE` and `MIN_MOVE_EPSILON` in `positionTracking.ts` are viewBox-unit constants (5% of the 300×200 diagonal; 0.01 units) — they operate on already-normalized `DriverDot` coordinates, not raw feed units.
- **`buildClosedTrackPath`'s closure search is O(n²) over the downsampled path** (nested loop over `path.length` up to 700, per `f1normalize.ts:819-827`). It's bounded and called only until closure succeeds (then never again per session), but a future change to `TRACK_PATH_MAX_POINTS` or `minDistance` should keep that cost in mind.
- **The trackPath cache is keyed per *meeting*, not per session** (`trackPathCacheKey`), and only ever written from the closed-trace branch of `adoptTrackPath`. Any new code path that could write an unclosed/unvalidated trace to that cache would corrupt the outline for every later session at that circuit — the existing guard is structural (open traces simply never reach `saveTrackPathCache`), so preserve that separation if refactoring `adoptTrackPath`.
- **`TRACK_PATH_CACHE_SCHEMA_VERSION` must be bumped whenever the shape or *semantics* of `buildClosedTrackPath`'s output changes** — not just its serialized format — since a stale-shaped-but-parseable cached entry from an older, buggier closer will otherwise be silently trusted (`f1normalize.ts:110-129` documents both historical bumps and why).
- **`positionTrackRef`, `labelPlacementsRef`, and `frameRef` are all plain mutable `useRef` maps holding cross-render state outside React's data flow.** They're intentional (avoiding re-renders on every animation/placement tick) but mean this widget's correctness depends on these refs being reset appropriately when the underlying session changes — `frameRef` explicitly checks `frameKey !== snapshot.session.id`; the other two are not shown resetting on session change in the read code, so a session switch that reuses driver numbers across different circuits could carry over stale label/track state until it's naturally overwritten by the first new frame's compute (worth verifying if a "switching sessions leaves visual artifacts" bug is ever reported).
- **Dead reckoning (`extrapolated: true`) only triggers in `isLiveSnapshot && hasCoordinatePositions` mode.** Replay and schematic mode dots never carry `extrapolated`, so any UI code branching on that flag must not assume it's meaningful outside live coordinate mode.
- **Label width estimation (`measureCharacterWidth`) is a hardcoded per-character approximation, not real font metrics** — if the label font, size, or weight ever changes, this table (and thus overlap-avoidance accuracy) will silently drift out of sync with what's actually rendered.
- **`markerBoxes` in `labelLayoutPlacement.ts` use radii (`10`/`8.5`) different from the actual rendered marker radii (`7`/`5.5` from `getTrackMapMarkerRadius`)** — intentionally larger, to keep labels clear of the marker's clickable/visual halo, not just its circle. Changing one without the other would either let labels crowd markers or waste placement space unnecessarily.
